# Что нужно доработать на бэкенде

Этот документ описывает расхождения между текущим фронтендом и бэкендом.
Фронт написан под описанный ниже функционал — бэк его пока не реализует.

---

## 1. Текущая сессия пользователя (`/users/current_session/`)

**Фронт ожидает:** GET-эндпоинт, который возвращает информацию об активной сессии пользователя.

**Тип ответа:**
```json
{
  "type": "nothing" | "pvp" | "training",
  "room_id": "123",
  "close_time": "2024-01-01T12:00:00Z"
}
```

**Зачем:** При перезагрузке страницы фронт должен уметь восстанавливать активную игровую сессию (PvP или тренировку) и перенаправлять пользователя обратно в комнату.

**Что реализовать:**
- Проверить есть ли у пользователя незавершённый `Round` со статусом `in_progress`
- Проверить есть ли незавершённая `Training`
- Вернуть соответствующий `type` и `room_id`

---

## 2. Статистика задач пользователя (`/users_statistics/count_of_solved/`)

**Уже есть** эндпоинт, но он принимает `user_id` как query-параметр и требует `IsAuthenticated`.

**Проблема:** Фронт профиля (`/profile`) показывает статистику текущего пользователя через `/users/me/`, который возвращает `stats` из `UserStatsSerializer`. Сейчас `stats` считает задачи через `training_statistics` и `round_statistics`. Если у пользователя нет записей в `UserTask` (таблица заполняется через `UserTask.objects.create()`), статистика будет нулевой.

**Что проверить:** Убедиться, что при завершении тренировки и PvP-раунда записи в `UserTask` действительно создаются. Сейчас в `TrainingConsumer.finish_training()` только меняется статус тренировки — `UserTask` не создаётся явно.

---

## 3. Статистика времени на задачу (`time_to_solve`)

**Фронт показывает:** `speed_train`, `speed_pvp`, `speed_total` в профиле.

**Бэк считает:** `Avg('time_to_solve')` по `training_statistics` и `round_statistics`.

**Проблема:** Поля `time_to_solve` в моделях не видно в предоставленном коде. Необходимо убедиться, что поле `time_to_solve` существует в соответствующих моделях статистики и заполняется корректно при завершении сессий.

---

## 4. Количество тренировок и PvP-матчей

**Бэк считает:**
```python
train_total = train_stats['total'] / 10 or 0
pvp_total = pvp_stats['total'] / 10 or 0
```
Делит количество задач на 10 (предполагая 10 задач в сессии).

**Проблема:** Если количество задач в сессии изменится — счётчик будет неверным. Лучше считать по количеству уникальных `Training`/`Round` для пользователя, а не делить на константу.

**Что реализовать:**
```python
trains_count = Training.objects.filter(player=user, status='finished').count()
pvp_count = Round.objects.filter(roundplayer__player=user, status='finished').count()
```

## 5. Поиск по предмету в PvP-матчмейкинге

**Фронт посылает** через WebSocket:
```json
{"type": "is_search", "is_search": true, "subject": 1}
```

**Бэк читает** `data['subject']` и передаёт в `matchmaking_service.find_enemy(subject=subject, ...)`.

**Что проверить:** Убедиться что в `start_round()` задачи фильтруются по переданному `subject`. Сейчас в коде это не очевидно из `RoundService`.

---

## 6. Удаление задачи из админки

**Фронт:** Не реализован UI для удаления задачи (специально, чтобы не делать опасный функционал без подтверждения).

**Бэк:** `TaskViewSet` с `ModelViewSet` и `permission_classes = [IsAdminUser]` поддерживает DELETE `/tasks/create/{id}/`.

**Что добавить на фронте (опционально):** Кнопка удаления задачи в `TasksSection` с подтверждением.

---

## 7. Редактирование задачи из админки

**Фронт:** Нет UI для редактирования задачи.

**Бэк:** `TaskViewSet` поддерживает PUT/PATCH на `/tasks/create/{id}/`.

**Что добавить на фронте:** Модальное окно редактирования задачи.

---

## 8. WebSocket аутентификация

**Бэк:** Middleware читает JWT токен из cookie (`access`) или query-параметра `token`.

**Фронт:** Использует `withCredentials: true` для HTTP. WebSocket соединения открываются без явной передачи токена — браузер автоматически отправляет cookie при WS-соединении на тот же домен.

**Что проверить:** Убедиться что в nginx/ASGI настройках cookie корректно передаются при WS handshake.

---

## 9. Восстановление PvP после разрыва соединения

**Текущее поведение бэка:** При `disconnect` consumer вызывает `technical_finish_round()` если раунд не завершён — это засчитывает технический проигрыш игроку который отключился.

**Проблема для фронта:** При случайном разрыве (потеря интернета) пользователь сразу получает технический проигрыш, без возможности переподключиться.

**Что реализовать:** Добавить grace period (например 30 секунд) перед тем как засчитывать технический финиш. Хранить состояние "игрок отключился" в Redis с TTL.

---

## 10. Рейтинговая история для обычного профиля

**Фронт (профиль):** Показывает только текущий рейтинг. История есть только в админ-панели через `AdminUsersListApiView`.

**Что добавить:** Эндпоинт или расширение `/users/me/` с историей рейтинга за последние N матчей — аналогично тому что уже реализовано в `AdminUsersListApiView`.
